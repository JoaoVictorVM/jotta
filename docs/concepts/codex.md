# Codex adapter

Codex reads its project configuration from `.codex/` and its repository skills from `.agents/skills/`. The adapter generates both from the harness files.

```bash
jotta adapter codex            # generate or refresh the Codex configuration
jotta adapter codex --dry-run  # show what would change
```

`jotta install` runs it next to the [Claude Code adapter](./claude-code.md).

## What is generated

| File | Content |
|---|---|
| `.codex/hooks.json` | `PreToolUse` on `Bash` and `apply_patch`, `PostToolUse` on `apply_patch` and `Stop`, each calling `jotta hook <event> --agent codex`. |
| `.codex/config.toml` | `approval_policy = "on-request"`, `sandbox_mode = "workspace-write"` and `network_access = false`. |
| `.codex/agents/<role>.toml` | A custom agent per role in `.jotta/agents/`, with `name`, `description` and the role as `developer_instructions`. |
| `.agents/skills/<skill>/SKILL.md` | The skill's name and description, and an instruction to read the canonical file. |

Codex loads `.codex/` only when the project is trusted, and runs a project hook only after it is reviewed and trusted with `/hooks`. A changed hook must be trusted again. After the first install, open Codex in the project, trust it and approve the Jotta hooks.

The hooks file is merged like the Claude Code settings: missing Jotta commands are added and everything else is kept. `config.toml`, agents and skills are written only when absent or generated by Jotta, so a file of yours is reported in `skipped` and never changed.

## How the hooks read Codex events

`jotta hook` answers in the protocol named by `--agent`. With `codex`, every answer exits with code 0 and a JSON object: `PreToolUse` blocks with a `deny` permission decision, and `PostToolUse` and `Stop` block with `"decision": "block"`, whose reason Codex feeds back to the agent.

Codex edits files through `apply_patch`, whose input is a patch that may touch several files. The hook reads every `Add File`, `Update File`, `Delete File` and `Move to` line and checks each file as its own edit, so a patch that touches one secret or one file outside the task scope is denied as a whole. A shell command sent as an argument list, such as `["bash", "-lc", "..."]`, is checked as the script it runs.

## Parity with Claude Code

| Capability | Claude Code | Codex |
|---|---|---|
| Block forbidden shell commands | `PreToolUse` on `Bash` | Same, on `Bash` |
| Block secret reads by file tools | `Read`, `Grep`, `Glob` and edit tools | No file read tool; reads go through the shell and are checked there |
| Task edit scope | `Edit`, `MultiEdit`, `Write`, `NotebookEdit` | Every file in an `apply_patch` |
| Smoke after an edit | `PostToolUse`, exit code 2 | `PostToolUse`, `"decision": "block"` |
| Receipt before stopping | `Stop`, exit code 2 | `Stop`, `"decision": "block"` continues the turn |
| Read-only reviewers | Tool list limited to `Read`, `Grep`, `Glob` | No per-agent tool list; enforced by instructions and the session sandbox |
| Skills | `.claude/skills/` | `.agents/skills/` |
| Approval and sandbox | Claude Code permission settings | `.codex/config.toml` |
| Activation | Hooks run once the settings file exists | The project must be trusted and each hook approved with `/hooks` |
